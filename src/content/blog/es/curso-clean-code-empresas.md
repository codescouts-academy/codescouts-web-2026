Cuando una empresa empieza a diseñar un plan de formación técnica para su equipo, la duda suele ser por dónde empezar: ¿arquitectura, testing, un framework concreto? En muchos casos, la respuesta más rentable es un **curso de Clean Code para empresas**, porque la legibilidad del código afecta a todo lo demás: a la velocidad de entrega, a las *code reviews*, al *onboarding* y a la capacidad de aplicar después prácticas como TDD o refactoring.

En este artículo explicamos qué problema resuelve la formación en Clean Code, qué debe cubrir un buen curso y qué preguntar a un proveedor antes de contratarlo.

## El problema que siente la empresa

El código se lee muchas más veces de las que se escribe. Cuando no es legible, el coste no aparece en una línea del presupuesto, pero se nota:

- **Las tareas tardan más de lo estimado**, porque entender el código existente lleva más tiempo que cambiarlo.
- **El *onboarding* es lento**: las personas que se incorporan necesitan semanas para moverse con soltura.
- **Las *code reviews* se atascan** en discusiones de estilo o, peor, se aprueban sin revisarse de verdad.
- **Cada desarrollador escribe a su manera**, y el código refleja quién lo hizo más que qué hace.
- **El miedo a tocar ciertas partes** frena cualquier mejora.

Ninguno de estos síntomas se arregla con una herramienta. Se arregla con criterio compartido.

## Qué es Clean Code (y qué no es)

Clean Code no es un reglamento rígido, sino un conjunto de principios para escribir código intuitivo y fácil de modificar. Tenemos un artículo introductorio sobre [Clean Code](/es/blog/clean-code/) si quieres repasar los conceptos.

Para una empresa, lo importante es que esos principios se conviertan en hábitos del equipo, y eso requiere práctica sobre código real.

## Qué debe cubrir un curso de Clean Code para empresas

En nuestro [curso de Clean Code](/es/courses/clean-code/) trabajamos estos bloques, con un volumen de práctica muy alto desde el primer minuto:

### Nombres y expresividad

Nombres que revelan intención, evitan comentarios innecesarios y hacen el código autoexplicativo. Es el cambio con mayor impacto y el más fácil de adoptar.

### Funciones y clases pequeñas

*Single Responsibility*, niveles de abstracción y las [4 reglas del diseño simple](/es/blog/4-reglas-del-disenio-simple/). El objetivo es que cada pieza de código tenga un motivo claro para existir.

### Code smells

Detectar duplicación, métodos largos, envidia de características u obsesión por los tipos primitivos. Un equipo que sabe nombrar los problemas los detecta antes.

### Refactoring higiénico

La *Boy Scout Rule* aplicada a diario: dejar el código mejor de lo que lo encontramos. Es la forma de mejorar un producto sin pedir semanas de "refactor" a negocio.

### Code review efectivo

Checklists de legibilidad y cómo dar feedback de código que el equipo acepta. Este bloque suele ser el que más agradecen los tech leads, porque convierte las reviews en un espacio de aprendizaje.

## Qué resultados esperar

Al terminar, el objetivo es que el equipo tenga:

- Código legible y autoexplicativo.
- Funciones y clases con una sola responsabilidad.
- Detección sistemática de *code smells*.
- El hábito de refactorizar de forma continua.
- *Code reviews* centradas en legibilidad.
- Una guía de estilo viva, acordada por el propio equipo.

## ¿Para qué perfiles tiene sentido?

Es el curso ideal para perfiles junior y también sirve para reciclar a seniors: todo el mundo escribe código a diario y la legibilidad impacta en todo lo demás. El nivel es básico y la duración es de 16 horas.

Por eso lo recomendamos a menudo como **primer curso de un plan de formación**: crea el vocabulario común sobre el que después se construyen TDD, refactoring de código legacy o arquitectura.

## Cómo evaluar a un proveedor de formación en Clean Code

Algunas preguntas útiles antes de contratar:

### ¿Se trabaja sobre código del equipo?

En nuestro curso refactorizamos código real del equipo aplicando nombres expresivos, funciones pequeñas, las 4 reglas del diseño simple y la detección de *code smells*. Es lo que hace que lo aprendido se aplique al día siguiente.

### ¿Cuánta práctica hay?

Un curso de Clean Code basado en diapositivas tiene poco recorrido. Pregunta qué porcentaje del tiempo se programa.

### ¿Cómo se sostiene después?

La guía de estilo del equipo y el foco en *code reviews* son la forma de que los hábitos sobrevivan cuando termina el curso.

### ¿Qué tamaño tienen los grupos?

Trabajamos con grupos de un máximo de 12 personas para garantizar atención personalizada.

## Cómo saber si la formación ha funcionado

Algunos indicadores cualitativos que conviene observar en las semanas siguientes:

- **Las *pull requests* son más fáciles de revisar**, con nombres claros y cambios acotados.
- **Las *code reviews* hablan de legibilidad** con un vocabulario común, no de gustos personales.
- **Los refactors pequeños forman parte del trabajo diario**, siguiendo la *Boy Scout Rule*.
- **Las personas que se incorporan entienden antes el código**.
